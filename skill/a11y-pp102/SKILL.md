# Доступность по ПП РФ № 102: аудит → атомарные правки → журнал

Скилл описывает процесс, а не стек. Работает с любым фронтендом: шаблонизаторы (Pug, Twig, Blade, Jinja), React/Vue/Svelte, CMS-темы (1С-Битрикс, WordPress), статическая вёрстка.

Справочники (читать по мере надобности, не все сразу):

- `references/requirements.md` — подпункты «а»–«н» п. 2 Требований: что значат, какие критерии WCAG им соответствуют, как проверять, типичные нарушения.
- `references/patterns.md` — готовые паттерны исправлений по компонентам (меню, диалоги, слайдеры, вкладки, пагинация, формы, видео, карточки, таблицы, документы).
- `references/pitfalls.md` — ловушки и регрессии, которые появляются именно при исправлении доступности.
- `references/testing.md` — методика ручной и автоматической проверки, включая масштаб 200%.
- `references/classification.md` — классификация замечаний (вёрстка / контент / бэкенд) и уровни критичности.
- `templates/audit-table.csv`, `templates/audit-table.md` — формат таблицы замечаний.
- `templates/fix-log.md` — формат журнала правок.

Скрипты проверки лежат в корне репозитория скилла, в `scripts/` (Playwright + axe-core). Если пользователь установил только папку скилла и скриптов под рукой нет — проверяй вручную по `references/testing.md`.

## 0. Применимость

Требования ПП № 102 обязательны для официальных сайтов государственных органов, органов местного самоуправления и **подведомственных им организаций** (государственные и муниципальные вузы, школы, больницы, музеи, библиотеки, МФЦ, бюджетные и казённые учреждения). Действуют с 01.03.2026. Для коммерческих сайтов прямой обязанности нет, но требования почти совпадают с WCAG 2.2 AA, поэтому методика применима к любому сайту.

Не давай юридических заключений («сайт соответствует закону»). Формулировка для отчёта: «замечания по подпунктам п. 2 Требований исправлены / остались такие-то».

## 1. Откуда берутся замечания

Два сценария:

1. **Есть готовый отчёт или таблица аудита** (от подрядчика, проверяющих, тестировщика) в любом формате: xlsx, csv, документ, тикеты. Прочитай его целиком, выпиши список пунктов с их кодами в исходном порядке. Коды — это идентификаторы пунктов, а не адреса ячеек; «пройдись от X до Y» — диапазон строк между этими кодами. Для xlsx без `openpyxl` хватит `zipfile` + разбора `xl/sharedStrings.xml` и `xl/worksheets/sheetN.xml`.
2. **Отчёта нет** — проведи аудит сам по `references/testing.md` (начни со сценариев: что пользователь должен сделать на сайте, и пройди это клавиатурой и скринридером) и заполни таблицу по шаблону `templates/audit-table.md`: один пункт — одна проблема в одном компоненте, с подпунктом ПП, критерием WCAG, шагами воспроизведения и рекомендацией.

Если замечание из отчёта нельзя привязать ни к одному подпункту «а»–«н» — это не повод его выкинуть: ставь критичность «улучшение» и исправляй в общем порядке.

## 2. Классифицируй каждый пункт до того, как писать код

По `references/classification.md`: **вёрстка** (чинит фронтенд), **контент** (нужны данные от автора: alt конкретной фотографии, расшифровка конкретного видео, реальные названия категорий), **бэкенд** (нужны данные или логика сервера). Фронтенд закрывает вёрстку полностью, а для контента готовит инфраструктуру (убирает мусорные дефолты, делает поле обязательным) и честно отдаёт остаток владельцу контента.

## 3. Сначала прочитай текущий код

Отчёт писался по скриншоту или сценарию и мог устареть:

- проблема могла быть уже исправлена — найди компонент поиском по коду и проверь в браузере;
- рекомендация может не ложиться на архитектуру — встраивай правку в API компонента (пропсы, параметры миксина), а не хардкодом в одном месте вызова;
- рекомендация может быть не лучшим решением. Отступать от неё можно, если суть проблемы (что теряет пользователь скринридера/клавиатуры) устранена. Отступление записывай в журнал.

## 4. Чини там, где проблема тиражируется

Перед точечной правкой проверь, где ещё используется тот же паттерн. Одна правка в общем месте закрывает пункты сразу на всех страницах:

- общий модуль слайдера → `inert` на неактивных слайдах везде;
- общий миксин карточки-ссылки → видимый `:focus-visible` на всех карточках;
- общий хелпер картинки → пустой `alt` по умолчанию вместо слова-заглушки;
- дизайн-токены цвета → контраст сразу во всех темах, включая версию для слабовидящих.

## 5. Один пункт — один короткий коммит

- Формат сообщения согласуй с пользователем; по умолчанию `<код пункта> <краткое название>`, например `FORM-01 Подписи полей формы обратной связи`. Несколько пунктов одного компонента можно объединить: `SRCH-01..04 Поиск`.
- Перед каждым коммитом спрашивай разрешения, если пользователь не разрешил коммитить без вопросов.
- Если общий фикс попутно закрыл пункт другого блока — отдельный пустой коммит не нужен, запиши связь в журнал.

## 6. Проверь, что ничего не сломалось

Исправления доступности часто меняют теги и структуру DOM, и это ломает JS, стили и интеграции. Обязательный минимум после каждой правки: функциональность компонента мышью, клавиатурой (Tab, Shift+Tab, Enter, Space, Esc, стрелки), со скринридером там, где менялась семантика, при масштабе 200%, в темах версии для слабовидящих, если они есть. Список известных регрессий — `references/pitfalls.md`, просмотри его перед правками форм, вкладок, пагинации, диалогов и слайдеров.

## 7. Журнал правок

В конце прогона — файл по шаблону `templates/fix-log.md`: пункт → статус → коммит → как исправлено. Обязательно:

- не скрывай несделанное: «в очереди», «контент», «бэкенд» — отдельными статусами;
- если пункт закрыт иначе, чем предлагала рекомендация, — одна строка, как именно;
- если один коммит закрыл несколько пунктов — отметь это у каждого;
- найденное по ходу, но отсутствующее в отчёте (регрессии, баги) — отдельный раздел «Не из отчёта».

## 8. Конфиденциальность

Отчёты аудита и код проекта принадлежат заказчику. Не переноси их тексты, адреса и фрагменты кода в другие проекты, публичные репозитории и примеры. В журнал и коммиты пиши только то, что касается текущего проекта.
